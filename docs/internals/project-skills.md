# Project skills management

The web/desktop chat header opens the project Skills popup. It uses the project's root and environment ID, rather than a thread's worktree or the primary environment. Settings → General configures a custom skills library per environment; the setting is searchable. There is no command palette, keybinding, or native mobile management entry point. Shared project atoms and typed WebSocket RPCs live in client-runtime and contracts, so no Electron IPC or browser-local filesystem access is required. Local, remote, relay, and tunnel connections use the same RPCs.

`ServerSettings.customSkillsPath` defaults to an empty string (disabled) and is persisted on each environment. `projects.skills.custom.list` reads immediate `<folder>/SKILL.md` entries only while Custom is selected, using bounded filesystem concurrency and the installed-description parser. There is no subprocess, network request, or polling. The list returns its resolved library path; `projects.skills.custom.install` checks that selection against the current setting to reject stale requests after a path change. Both RPCs use the same read/operate scope split as other skills operations.

Custom installs copy regular files and directories directly into both project skill roots under the same mutation semaphore as CLI installs/removals. Source files remain unchanged; linked entries and project destinations outside the project are rejected. Existing folders, including partial copies, are never overwritten. Exclusive directory creation reserves destinations, and failures clean up only directories created by that operation. Stale lockfile provenance for the selected name is removed while preserving other entries; no new remote source is fabricated. The Custom tab reports name occupancy as In project, without implying content equality. Updating a custom copy uses the existing remove flow followed by installation. Clearing the setting neither deletes the library nor uninstalls project copies.

`ProjectSkills` owns the server integration. The popup opens on Installed; no remote search is subscribed until Browse is selected. There is no bundled skill catalog or automatic skill installation. Browse independently fetches eight starter entries using an empty query, which searches the `agent` topic. Further queries fetch at most twenty entries from the same `https://skills.sh/api/search` endpoint as the official CLI's `find` command. Each directory entry is validated separately: unsupported hosted-domain sources or malformed entries are skipped without hiding installable GitHub results. Unexpected response shapes, HTTP errors, timeouts, and connection failures have distinct messages.

The client retains up to 200 discovered metadata entries per environment, replacing duplicates by source and name and evicting older entries. Local filtering runs immediately; remote search uses a 350 ms debounce and requires at least two characters. Search submit bypasses the delay. Only results for the current input are displayed; other queries can contribute cached metadata without showing unrelated rows. Cached matches remain usable during loading or failure. Query results are fresh for thirty minutes; queries and catalog atoms expire after thirty idle minutes. Refresh explicitly re-fetches the current query or starter selection. There is no background polling, full-directory download, or disk-persistent catalog. Installed queries run only while the popup is mounted.

`ProjectSkillsDiscovery` reads only the project's `.agents/skills` and `.claude/skills` directories. Entries must be directories containing a `SKILL.md` file; linked directories work, dangling links and non-skill entries are ignored. Directory names identify skills and matching names are merged across the two locations. Filesystem checks have bounded concurrency. Description discovery reads at most the first 16 KiB of each skill file and parses only its YAML frontmatter; missing, malformed, unreadable, or oversized headers do not hide the skill. Descriptions are normalized and capped at 2,048 characters. When copies differ, an available `.agents` description takes precedence. Optional provenance comes from `skills-lock.json`; missing or damaged metadata does not hide installed files. Missing skill directories are empty, while other directory errors are surfaced. Listing requires neither a subprocess nor network access and does not wait for CLI mutations.

Browse descriptions use a separate read-scoped `projects.skills.describe` RPC. It runs only after the row's Description control is opened, unless the same installed skill already provides a local description. The skills.sh search API does not supply descriptions; the server extracts the matching `SoftwareApplication` JSON-LD description from the public skill detail page. Page HTML is never executed or rendered. This page metadata is an external integration boundary: missing or changed markup returns no description instead of fabricating one. Downloads are capped at 2 MiB with a ten-second timeout. Description queries are cached for thirty minutes per environment, source, and name, independently of search and installation.

Install and remove run `npx --yes skills@1.5.23` through the existing process runner, which handles Windows command shims, closed stdin, cancellation, output limits, and timeouts. The version is pinned to keep mutation behavior stable. Add selects one named skill and both `codex` and `claude-code` with `--copy --yes`. No global flag is used. Removal omits the agent filter so the CLI can delete a canonical skill shared by multiple installed providers, including other project copies of that named skill. The UI states this scope explicitly. Mutations are serialized in one server-lifetime service to avoid concurrent project lockfile writes across clients, and verify the resulting files directly. No operation writes T3's live database.

Listing and search require orchestration read scope. Install and remove require orchestration operate scope. Sources are GitHub `owner/repo` identifiers; names cannot contain flags, wildcards, or path traversal. Installs refuse to replace a same-name skill from a different source or a manually installed skill without provenance. Mutations verify the resulting installed list instead of trusting the CLI's exit code alone and refresh the list even on failure, since an operation can partially write files.

Codex, Claude, Cursor, and OpenCode discover project skills through the shared and/or Claude directories using their existing adapters. Grok uses `.grok/skills`, which this feature does not populate. Providers retain their existing reload behavior; user documentation advises starting a new session when needed. This feature neither changes provider protocols nor adds orchestration events.
